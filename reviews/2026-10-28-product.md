# spec-ctx: product review before the next commit

Reviewer: product manager, developer tools. Date: 2026-10-28. Read only.

## The user and the job

The user knows OpenSpec and runs Claude Code or Codex. They have seen an agent tick a box for work that does not pass. They have paid for an agent that read the whole `openspec/` tree to change one function.

The job: "I describe a change once. The agent plans it, builds it, proves each task, and archives it. I step in only where my judgment matters. A ticked box means a passing command."

They do not hire spec-ctx for IDs, bundles, or linters. They hire it for less context per task and a done that cannot be claimed without proof.

## What they get today and where they fall off

What works:

- context_ratio 0.043 over 54 tasks.
- evidence_ratio 0.87 overall, 1.00 on every change since 002.
- 36 of 70 reopens flagged by `check --strict` first.
- Median 71 s per task.
- `adopt` wrote 1,625 IDs into the fork in 1.5 s, and the upstream CLI kept working.

Where a stranger falls off, in order:

1. Two tools, two hints. `openspec init` says "run `/opsx:propose`". Run before `specctx init --all`, that gives headers with no IDs.
2. Nothing chains the steps. The user must know about 12 commands and three skills. The fork transcript wrote every artifact by hand.
3. Upstream `/opsx:apply` breaks the core promise. Its steps say to edit `- [ ]` to `- [x]` and to read every file in `contextFiles`. The schema's `apply.instruction` still says "mark complete as you go". `operations.apply.guidance` cannot win, because the apply skill drops guidance that conflicts with its built-in steps. `check --strict` catches the hand tick, but late.
4. The release lags `main`. The guide names 0.1.3, which is not on npm.
5. The fork is a second install: a tarball, a package renamed twice, and a config edit so the gate runs it.
6. On an existing project the loop gives nothing. 0 of 118 open tasks had a REQ or a Verify span.
7. CAP codes in families such as `cli-*` are unreadable (`CLV`, `CV`, `CLIC`).
8. The gate lints the adopter's prose with the owner's STE rules: 11 s on 659 files for rules the adopter never chose.
9. `status` skips changes with no `tasks.md`.

The core holds. The fall off is in the seams between the two tools and in what the user must remember.

## The one prompt experience (Q3)

The user must know two things: `npx -y spec-ctx init --all` once, and the skill `/specctx-run`.

1. The user types `npx -y @fission-ai/openspec@latest init --tools claude`, then `npx -y spec-ctx init --all`. The last line is `next: /specctx-run <what you want to build>`.
2. The user types `/specctx-run add a greet(name) function with a default of world`.
3. The agent runs `specctx status --json` and gets `next.action: plan`. It says "No active change. Planning add-greeting."
4. The agent follows the upstream `openspec-propose` skill. The ID rules reach it through `openspec instructions`. It takes IDs from `specctx id new`. Each task cites a REQ and ends with a Verify command.
5. The agent runs `specctx check --strict` and `openspec validate <change> --strict`. A finding sends it back to step 4.
6. The agent stops. The propose skill already has a planning boundary, so this stop costs nothing to build. The user sees the tasks with their Verify commands and one question: "The plan has 3 tasks. Each closes only when its command passes. Build it?"
7. The user types `go`, or asks for edits.
8. The agent loops on `status --json`. Each `work <task>` action means `task start`, the code with REQ tags, and `task done`. The user sees `done add-greeting/1.1. Evidence: ...` and the agent moves on.
9. On a Verify failure the user sees the red line and a one line fix plan. After 3 failed runs of one task, the agent runs `handoff ask` with the failure tail and `handoff write`, and stops with one plain question.
10. With every task done, the action is `gate`. The agent runs `specctx gate --strict`. A finding becomes a `fix` action under the same cap.
11. On a green gate, the action is `archive`. The agent follows the upstream `openspec-archive-change` skill and answers through the user if it asks to confirm. Then `handoff write` and `stats --change`.
12. The user sees "Archived add-greeting. 3 tasks, 3 with evidence, bundle 4 percent of the spec text, 6 minutes." A new session resumes with `/specctx-run` and no argument.

### Where the state machine lives

In the files that exist today. No new state file.

- Planning state: the OpenSpec artifact graph, owned by `openspec status`. spec-ctx does not copy it.
- Task state: the checkbox plus the evidence file, as ADR-004 says.
- Human gates: the handoff's open questions. Plan approval is one of them.
- The next action: a pure function of those files. Add `next: {action, target, reason}` to `status --json`, with fixed verbs `plan`, `cite`, `work`, `fix`, `wait`, `gate`, `archive`, `none`. The human output already prints a `next:` line.
- Retry counts: an append-only verify log beside `gate-log.jsonl`. A log is a record, so it duplicates nothing.
- `current.json` stays only as the start time for cycle time. The driver never reads it for the next task.

### Deterministic, and what the LLM decides

The engine decides the next action, whether a task is done (exit code), whether a change may archive (gate exit code), the retry count, the IDs, and the bundle.

The LLM decides the plan, each Verify command, the code, the fix for a failure, and when a question needs a human. The human reads the Verify commands at the plan stop. That review is the main defense against a weak command such as `true`.

### The skill set

One skill, `specctx-run`, under 60 lines. It holds the loop and names the upstream propose and archive skills. It replaces `specctx-bootstrap`, `specctx-next`, and `specctx-done`. Keep those as aliases for one release.

The driver never calls `/opsx:apply`. Set the schema's `apply.instruction` to "Close each task only with `specctx task done`. Do not edit checkboxes." That covers a user who types `/opsx:apply` by habit.

## Q1. task backfill

Recommendation: remove it in the next minor release, and drop it from the README existing path.

Why: the baseline already records legacy done tasks as done without evidence. Two mechanisms for one debt means two things to explain and fix. On the fork, backfill made the review diff 20 times the spec diff. A note that says "adopted" proves nothing and dilutes evidence_ratio.

What we give up: a per task note on legacy work. `task done --manual` still gives one to a user who wants it.

## Q2. The fork

Recommendation: stop shipping the fork. Users install upstream OpenSpec only. Freeze `spec-ctx-adopt` as the reference for a pull request that the owner offers only when a maintainer asks on #1967.

Close the one gap the fork covers inside spec-ctx. Upstream archive refuses a MODIFIED header whose title changed, and upstream `validate --strict` only prints INFO for it. Add a `check` rule for a delta header whose ID matches a main requirement but whose title differs. The finding prints the RENAMED block to paste, or says to keep the main title.

Why: upstream ships often. A fork costs a rebase and a release each time, and a second install for each user. The ID already rides through upstream archive as header text.

What we give up: a silent rename by ID, and scenario matching by ID inside upstream validate, until upstream takes the change.

## Q3. Closed loop automation

Recommendation: the design above. One skill, one JSON oracle in `status`, state in existing files, two human stops that upstream skills already make, and a retry cap of 3 that ends in a handoff question.

Why: it adds one field, one log, and one skill. It reuses the upstream artifact graph, propose and archive skills, the open questions, and the evidence. Each tool owns its part of the state. Our skill calls upstream skills by name and copies none, so upstream changes to planning do not break it.

What we give up: a fully unattended run. Removing the plan stop means forking the propose skill. I would keep the stop anyway, because it is where a human checks the Verify commands. We also give up control of planning order.

## Q4. What to cut

- `task backfill`. See Q1.
- The fork release: `@sonqh/specctx-openspec`, its tarball and binaries, and its guide. Move the guide into the spec-ctx repo, written for upstream.
- The three skills, merged into `specctx-run`.
- The copied schema in `schemas/spec-driven-ids/`. It holds a full copy of upstream instruction text, so it drifts on each upstream release. Move the ID rules into `openspec/config.yaml` `rules`, which upstream adds to each artifact's instructions (REQ-RI-005). Keep a schema of a few lines only if `apply.instruction` needs it. We lose the templates with ID placeholders, so test that rules alone give IDs before the cut. If they do not, keep the bundle and add a test that diffs it against upstream.
- The linters in the adopter's default gate. `init` writes `[gate] markdown = []`. Later, move `lint tells` and `lint ste` back to the ste-humanize skill, which they track (change 009).
- Release binaries. The tool needs Node 22 and runs through `npx`.
- `npx skills add` as a second install path.
- REQ-DIST-006 and REQ-DIST-007. They record history, not behavior.
- The resolved list in `handoff.md`. It grows forever and the agent reads it at each start. Git history keeps it.

## Q5. Rollout

A stranger installs Node 22, upstream OpenSpec with `init --tools <tool>`, and `npx -y spec-ctx init --all`. No fork, no config edit.

The first 10 minutes on a fresh project:

- Minute 0 to 1: the two init commands.
- Minute 1 to 4: one prompt. The agent plans and stops at the plan.
- Minute 4 to 9: `go`. Tasks close with evidence, and the gate goes green.
- Minute 9 to 10: archive and the stats line.

On an existing project: `init --all`, `adopt --dry-run`, `adopt`, `baseline write`, then `/specctx-run <change>`. The first action is `cite`. The agent lists the change's requirements with `query --change <change> --kind req`, adds a REQ and a Verify span to each open task, and stops for approval.

What blocks a stranger today:

- The fixes on `main` are not on npm.
- `/opsx:apply` ticks by hand, and nothing steers the user away from it.
- There is no single entry point.
- The rename case needs the fork.
- CAP codes on large repos are unreadable. `adopt` needs a family prefix pass (friction item 4).
- The Action `uses: sonqh/spec-ctx@v0` needs a public repo. An old handoff entry says the repo was private. Confirm before any announcement.

## Rollout plan

### Phase 0. Clean base (0.2.0)

Ships: the unreleased fixes, no `task backfill`, the retitle rule, linters off for adopters, the `apply.instruction` fix, the guide in the spec-ctx repo, and no more fork releases.

Measure: `tests/paths/fresh.sh` and `existing.sh` against upstream `@latest`. Gate pass rate on a fresh project with default config. A dogfood rerun on the OpenSpec repo: commit size and gate result.

Exit: both path tests pass on upstream with no fork. The fresh path ends with `gate --strict` exit 0 and no config edit. The dogfood commit holds no evidence files.

### Phase 1. The driver (0.3.0)

Ships: `next` in `status --json`, the verify log, `specctx-run`, and the old skills as aliases.

Measure on spec-ctx, then on two small public repos, on Claude Code and on Codex:

- Human stops per archived change. Target 2.
- evidence_ratio on new changes. Target 1.00.
- Hand ticks caught (`done-without-evidence`). Target: none reach archive.
- Verify first pass rate, from the verify log.
- Cycle time per task and per change.
- Gate pass rate on the first gate run of each change.
- context_ratio, which must stay under 0.07.

Exit: five changes in a row on spec-ctx archived through `/specctx-run` with only the two stops and evidence_ratio 1.00. One change archived the same way on Codex.

### Phase 2. Proof in CI (0.4.0)

Ships: the Action reruns the Verify command of each task closed in the pull request and compares the exit code with its evidence. A `check` rule flags a weak Verify such as `true`, `exit 0`, or a lone `echo`.

Measure: replay mismatches, flaky replays, the share of weak Verify commands, and stale_catches over reopens.

Exit: two weeks of replay on spec-ctx and one external repo with zero flaky failures, and each mismatch traced to a real cause.

### Phase 3. Strangers

Ships: a note on #2157 and the README with the positioning below. The family prefix pass in `adopt`.

Measure: time to the first archived change per new user, the step where each user stops, and the share of existing path users who get past `cite`.

Exit: three people the owner does not know each archive a change through `/specctx-run`. The owner then decides whether to offer the ID matching upstream.

## Do not build

- An LLM call, a daemon, or a file watcher in the engine.
- A new state file for the loop, the phase, or plan approval.
- A copy of the OpenSpec artifact graph, or a planner in spec-ctx.
- Forks of the upstream propose, apply, or archive skills.
- A mode that skips the plan stop.
- Automatic REQ citations for legacy tasks by text match. The agent proposes them, the human approves.
- Retries with no cap.
- Semantic search, a dashboard, or an MCP server before Phase 3 shows a need.
- Adapters per agent tool. The skills are plain markdown.
- New lint rules for adopter prose.

## Positioning

To an OpenSpec user: "spec-ctx gives each requirement in your OpenSpec project an ID, hands your agent only the spec text one task needs, and closes a task only when its Verify command passes. Type `/specctx-run` with what you want, and the agent carries the change from proposal to archive, stopping for you at the plan and at archive." To the user, spec-ctx is an add-on to upstream OpenSpec, not a fork. It installs with one command next to the OpenSpec they already have. It uses OpenSpec's own extension points: config rules, the schema's apply instruction, and skills that call upstream skills by name. So it keeps working across upstream releases with no rebase. The ID matching that the fork proved sits as a proposal on #1967. It becomes a pull request only when the owner and a maintainer agree. If upstream takes it, the user sees one spec-ctx check go quiet, and nothing else changes.
