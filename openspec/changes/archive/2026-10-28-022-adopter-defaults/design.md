# Design

## Decisions

- D1 `defaults().gate.markdown` is `[]`. `INIT_TEXT` writes `markdown = []` under `[gate]` with a comment that names the globs to set when a project wants the lint, and says that the spec-ctx repository opts in. The key count of SCN-DIST-002-2 stays 13. `gate` with no key and no `--markdown` prints `linters: ok (0 file(s))`.
- D2 `detectOpenspec()` in `src/init/init.ts` returns the value of `SPECCTX_OPENSPEC` when the env var is set. Else it runs `npx -y @fission-ai/openspec@latest --version` with `spawnSync` and a 60 second timeout, takes the first `\d+.\d+.\d+` of stdout, and returns `npx -y @fission-ai/openspec@<version>`. On a non zero exit, a timeout, or no version in the output it returns the default. It also returns the note `note: could not read the OpenSpec version. [gate] openspec uses @latest.` The detection runs only when `init` writes `spec-ctx.toml`. An existing file stays as it is, so no detection runs for it. `configText(root, openspec)` puts the value into the `openspec = ` line.
- D3 Tests never hit the network. `Project.runIn` in `tests/helpers.ts` sets `SPECCTX_OPENSPEC` to the default for the span of an `init` call when the env var is absent. The init tests set the env var on their own where the written value matters. One test spawns `dist/cli.js init` with a `PATH` that holds a fake `npx` which prints `9.9.9`, and reads `@9.9.9` from the file. A second spawn with a fake `npx` that exits 1 reads `@latest` and the note.
- D4 `mergeConfig` merges `rules` and `operations` item by item when the key exists in the project config. For each second level key of the fragment (`rules.specs`, `operations.apply.guidance`) it finds the same list in the project block. A fragment item whose value, with its YAML single quotes removed, equals a project item is skipped. Other items are appended after the last item of that list with the indent of that list. A second level key that the project lacks is appended to the block as a whole. The result gains `merged: {key, added}[]`. `runInit` prints `merged openspec/config.yaml <key> (<n> added)` for a merge that added items and `kept openspec/config.yaml <key>` for one that added none. A merge that adds items counts as a write for the `nothing to do` check.
- D5 `GITIGNORE_LINES` gains `.ctx/current.json` and `.ctx/gate-log.jsonl`. The fresh output is `wrote .gitignore (4 lines)`. The `nothing to do` check reads all four lines. This repository's `.gitignore` gets `.ctx/current.json`. It has `.ctx/gate-log.jsonl` since 017.
- D6 `src/handoff/questions.ts` owns `.ctx/questions.json`: a JSON list sorted by `n` of `{n, asked_at, task, text, status, answer?, resolved_at?}`. `status` is `open` or `resolved`. `ask` appends with `n` one above the highest `n` in the file, `asked_at` from `isoNow()`, `task` from `current.json`. `resolve <n> <answer>` sets `status`, `answer`, `resolved_at` on the open question with that `n` and exits 2 with `no open question <n>` otherwise. The file is committed, so it is not in `.gitignore`.
- D7 `handoff.md` stays a view. `renderQuestions` writes each open question as `- Q<n> <text> (task <task>, <date>)` and each resolved one as `- Q<n> <text> (task <task>, <date>) answer: <answer>`. The resolved list shows the last 10 by `n`, then one line `- and <k> more in .ctx/questions.json` when more exist. `writeHandoff`, `ask`, and `resolve` all render from the file. `parseHandoff` still reads the lists, for the migration only. `status` reads the open questions from `questions.json`.
- D8 Migration. When `questions.json` is absent and the previous `handoff.md` holds `open_questions:` or `resolved:` items, `writeHandoff` parses each item with the pattern `<text> (task <task>, <date>)[ answer: <answer>]`. Resolved items come first, then open ones, with `n` from 1 in that order. `asked_at` is the date of the item. It writes the file once and returns `migrated: <n>` on the result. `handoff write` prints `migrated <n> question(s) to .ctx/questions.json` before `wrote .ctx/handoff.md`. An item that does not match the pattern becomes a question with the whole item as `text` and `task` `none`.
- D9 `handoff ask` prints `open question <n> added` with the `n` of the new question, so the number in the output is the one `handoff resolve` takes.

## Risks / Trade-offs

- A project that relied on the old default globs and has no `[gate] markdown` key loses the lint step of its gate. The README names the key, and the comment in the written file says how to turn it on.
- A pinned version means a project does not follow upstream releases. That is the point. `init` writes the pin once, and the user edits it.
- A merge of `rules` items appends text to a file that the user owns. The items are plain strings and the merge adds nothing that exists. `repairItems` runs after the merge, as before.
- The resolved list in `handoff.md` is now shorter. The full list stays in `questions.json`.
