# Design

## Decisions

- D1 `specctx next [--json] [--change <c>]` is a read command. It writes no file. With `--json` it prints one object with nine keys, sorted: `action`, `attempt`, `change`, `command`, `human`, `max_attempts`, `reason`, `state`, `task`. Every key is present in every state. A key without a value is `null`. `attempt` is `0` when no fail file counts. `change` is the folder name under `openspec/changes/`. `task` is the task ID as `tasks.md` and the evidence use it, so `<key>/<n.n>`. The human form prints `action: <a>` first, then one line per other key in sorted order with `none` for `null`, and the last line is `next: <command>`. The `command` key has no line of its own, because `next:` carries it. Exit 0 when the project parses, 2 on a usage error, 3 on an unreadable tree.
- D2 The decision order, first match wins. Step 0 picks the change: the folder that `--change` names, else the lowest folder name under `openspec/changes/` except `archive`, with the same order as `task next`. The folders come from the file system, not from the index, so a change with no `tasks.md` yet still counts as active.
  1. No folder, or `--change` names none: `plan`, `human: true`, `command: <openspec> new change <name>`, `reason: no active change` or `reason: no change <c>`, `state: no_change`.
  2. An open question in `.ctx/questions.json` whose `task` is the folder, its key, or starts with `<key>/`: `ask`, `human: true`, `reason` is the question text, `command: specctx handoff resolve <n> "<answer>"`, `state: question_open`. A question with `task: none` blocks nothing.
  3. `<openspec> status --change <folder> --json` fails: `stop`, `reason: openspec status failed (exit <n>): <first line>`, `state: openspec_failed`. It reports `isPlanningComplete: false`: `plan`, `human: true`, `command` is `nextSteps[0]`, or `<openspec> status --change <folder>` when the list is empty, `state: planning`. The engine reads no other key.
  4. `check --strict` on the files of the change, after the baseline, has a finding with the rule `missing-id`, `task-without-req`, `task-without-verify`, or `unknown-task-req`: `cite`. `task` is the ID of the first finding on a task line in file and line order, or `null` when every finding is on a header. `command: specctx query --change <folder> --kind req`, `reason: <rule> <id> at <file>:<line>`, `state: citation_missing`.
  5. A `[x]` task of the change with no evidence file: `repair`, `command: specctx task done <t>`, `state: done_without_evidence`.
  6. `.ctx/current.json` names an open task of the change. `attempt` is the count of its fail files in the window of D4. `attempt >= max_attempts` and no open question for the task: `ask`, `human: true`, `command: specctx handoff ask "<question text of D5>"`, `state: attempts_exhausted`. `attempt > 0`: `fix`, `reason: Verify failed (exit <e>): <first line of the last tail>`, `command: specctx task done <t>`, `state: task_failed`. No fail file: `work`, `command: specctx task done <t>`, `state: task_started`.
  7. An open task exists: `start`, `task` from the same order as `task next`, `command: specctx task start <t>`, `state: task_open`.
  8. The last line of `.ctx/gate-log.jsonl` is not `ok: true`, or its `at` is before the `at` of the newest live evidence file of the change, or the log is absent: `gate`, `command: specctx gate --strict`, `state: gate_due`. The log is per session, so a fresh clone runs the gate once more. That is the accepted cost.
  9. Else `archive`, `human` is `[loop] archive == "ask"`, `command: <openspec> archive <folder> -y`, `state: gate_passed`.
  10. No rule matched: `stop`, `reason: no rule matched`, `state: unknown`. The order above leaves no such state, so this is the guard, not a path.
- D3 `<openspec>` is `process.env.SPECCTX_OPENSPEC ?? cfg.gate.openspec`, the same resolution as `gate`. `next` runs `<openspec> status --change <folder> --json` with `/bin/sh -c` in the root and a 60 second timeout. It parses stdout as JSON. A non zero exit, a timeout, or text that is not JSON gives the `stop` of step 3. Tests point `SPECCTX_OPENSPEC` at a shell script in the temp project that prints canned JSON, so no test reaches the network.
- D4 A non zero Verify exit in `task done` writes `.ctx/evidence/<c>/<t>.fail-<n>.json` with the sorted keys `at`, `attempt`, `stderr_tail`, `task`, `verify`. `verify` has `command` and `exit`, with `exit: null` on a timeout. `stderr_tail` holds the last 20 lines of the combined output, the same text that `task done` prints, because a test runner writes its summary to stdout. `attempt` is the count of fail files of the task inside the window plus one. The window starts at `current.json.started_at` when `current.json` names the task, else at the first fail file. A resolved question whose `task` is the task moves the window start to its `resolved_at`, so `handoff resolve` resets the count and the loop can retry. `<n>` in the file name is the next free number over every fail file of the task, so a file is never replaced. A passing run keeps the fail files. `listEvidence` and the evidence reader of `stats` skip a name that matches `.fail-<n>.json`, so `check`, `stats`, and `handoff` never read one as evidence.
- D5 When `attempt` reaches `[loop] max_attempts` and no open question names the task, `task done` appends a question through `addQuestion` with the task ID and the text `task <t> failed Verify <n> times. Last: <first line of the tail>. What should change?`. An empty tail gives `Last: no output`. After the usual failure text it prints `blocked: question <k> written. Run specctx handoff resolve <k> "<answer>" to continue.`. When an open question for the task exists already, it prints the same line with that number and adds none. The exit code stays 1. With `--json` the failure object gains `attempt`, `fail` with the file path, and `question` with the number or `null`.
- D6 `Config.loop` is `{ max_attempts: number; archive: "ask" | "auto" }`. `loadConfig` rejects `max_attempts` that is not an integer of 1 or more with `spec-ctx.toml: loop.max_attempts must be an integer of 1 or more.` and `archive` that is not `"ask"` or `"auto"` with `spec-ctx.toml: loop.archive must be "ask" or "auto".`. `INIT_TEXT` gets a `[loop]` section with one comment per key. The key count of SCN-DIST-002-2 goes from 14 to 16.
- D7 `next` joins `COMMAND_FLAGS` with `change: "string"` and the help table under `Read`. The summary, the flag text, and every error string pass `lint ste --baseline 0`. The help golden is recorded again.
- D8 `tests/loop/next.test.ts` copies the no-ID fixture to a temp project. It walks the project through every state of D2 in order, with the stub of D3 and `SPECCTX_NOW` fixed. One test holds the expected object for each state. One test asserts that every `action` over all states is in the closed list. One test asserts that the human form starts with `action: `, ends with `next: `, and passes `lint ste --baseline 0`.
- D9 `handoff write`, `status`, and the skills do not change. The `specctx-run` skill of ADR-006 item 3 is a later change.

## Risks / Trade-offs

- `nextSteps[0]` is a sentence from OpenSpec, not a shell command. The skill that reads `plan` passes it to the agent as text. Upstream can change the shape. The gate pins the version, so that is a known failure.
- The gate log is per session. A fresh clone with every task done gets `gate` once, then `archive`. One extra gate run is cheaper than a tracked log.
- A fail file lives next to the evidence. Any reader of `.ctx/evidence/` that does not use `listEvidence` must skip the pattern. `stats` has its own reader, so it gets the skip in this change.
