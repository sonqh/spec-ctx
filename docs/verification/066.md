# Verification of change 066-stale-by-tag

Date: 2026-11-07. Branch `feat/066-stale-by-tag`, stacked on 064 and 065. ADR-010 item 3.3.

## The problem in numbers

`task done` used to record every code and test file that carried a tag of a cited requirement. The count over the 27 live evidence files of changes 059 to 065:

- 165 recorded files. 107 of them (65 percent) are in no task line and in no Verify command. A tag put them there.
- 23 of the 27 evidence files hold at least one such file.
- 40 of the 107 sit in a file that the change commit never edited, so no task of that change touched it.
- 23 `reopened` copies exist for those changes.

Method. A scratch script read each evidence file of `.ctx/evidence/<change>/`. A file is named when it is in the `paths` of the task entry or in a token of the Verify command. Every other recorded file is tag-only. A tag-only file is foreign when `git diff` of the change commit does not list it.

## The rule now

`task done` records the files that the task line names, the files that its Verify command names, and the files that the git diff touched since `task start`. `task start` writes `base` into `.ctx/current.json`. New evidence has a `diff` field. A tag alone adds nothing. Tests: `tests/tasks/files.test.ts` (unit), `tests/tasks/stale-by-tag.test.ts` (through the CLI), `tests/tasks/evidence.test.ts`.

## Replay of the case

Task A cites REQ-X, which `src/f.ts` carries as a tag. Task B edits `src/f.ts`.

- Before: A is `stale-evidence src/f.ts` and needs a repair.
- After: A has `files` of `{}` and stays fresh. `check --strict` reports no finding for A. B records `src/f.ts` in `files` and in `diff`. The test is the first case of `tests/tasks/stale-by-tag.test.ts`.

A second case proves that no recorded file comes from a tag alone: every key of `files` is in `diff` there.

## The loop of this change

- Stale-evidence repairs: 1. Task 1.1 closed before the code of task 2.1 existed, so the old tag rule wrote its evidence. It held `src/tasks/evidence.ts` and `tests/tasks/evidence.test.ts`, which task 2.1 then edited. `next` named it. `task reopen 066/1.1` and `task done 066/1.1` fixed it, with no `task start`. The new evidence holds only `src/tasks/files.ts` and `tests/tasks/files.test.ts`.
- From task 2.1 on, `task done` used the new rule. No later task became stale.
- Task 2.1 closed after a second `task start` that ran on the new build, once the code worked. Its `diff` is empty for that reason. Its named files are in `files`.
- Verify failures: 1. Task 3.2 failed once, on the stale 1.1 evidence, through `tests/gov`.

## Costs and limits

- A repair run has no `task start`. It carries the `diff` paths of the newest reopened copy (REQ-TASK-010). Evidence from before this change has no `diff` field, so nothing comes back from it.
- `git` is the only extra process. A project with no git, or a repo with no commit, records the named and Verify files and prints one note on stderr.
- The git calls drop `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, and `GIT_PREFIX` from the environment. A hook such as `pre-push` sets them, and they would point the calls of a test at this repo.
- A repo with no commit gives the cause `no git repo` in the note.
