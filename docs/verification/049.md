# Verification of change 049-index-same-ms-stale

## Tasks

- 049/1.1 `src/index/clock.ts` reads the file system clock and sets the index mtime. `buildIndex()` waits for the file clock to pass a newest file 0 to 50 ms after T0, then builds once. The walk skips `.ctx`. `tests/index/same-tick.test.ts` covers SCN-IDX-004-2, SCN-IDX-004-4, and SCN-IDX-014-1 to SCN-IDX-014-5.
- 049/2.1 This record and the CHANGELOG entry.

## Layer

- Layer 1, retrieval. Every answer of `query`, `related`, `bundle`, and `task start` comes from the index. The change removes a window where that answer was wrong.

## Before the fix

- The planning probe gave 73 stale reads in 3,000 write, `check`, write sequences. That is 2.4 percent.
- A re-run of the planning engineer on the old engine gave 0 in 1,000.
- The same probe in this build gave 132 stale reads in 1,000 on the old engine. The rate depends on the clock tick against the speed of the engine. It is not a stable number.
- The forced-mtime test is the real evidence. A rewrite takes the mtime of the first write, 60 s ahead. The old engine keeps the old index. The run of `tests/index/same-tick.test.ts` on the old engine, before any engine edit, gave 4 failures and 4 passes:
  - SCN-IDX-004-4, forced mtime: `task start` printed nothing.
  - SCN-IDX-004-4, 30 sequences: 2 stale reads.
  - SCN-IDX-014-2: no `index rebuilt` when the newest file sat at the index mtime.
  - SCN-IDX-014-4: `src/index/clock.ts` did not exist.

## After the fix

- The probe gave 0 stale reads in 3,000. All 8 tests of `tests/index/same-tick.test.ts` pass.
- `bun test tests/loop tests/cli` ran 30 times in a row. All 30 runs exited 0 with 160 pass and 0 fail.
- Times on this repository, median of 15 runs of the CLI, two rounds each:

| Command | Old engine | New engine |
| --- | --- | --- |
| `build` | 384 ms, 401 ms | 351 ms, 359 ms |
| `query REQ-IDX-004` | 145 ms, 171 ms | 143 ms, 135 ms |

- The ADR-007 speed notes list 25 to 40 ms for the freshness walk and 10 to 20 ms for the query. The clock reading adds one small file create, stat, and delete to each load. The difference stays inside the noise of this machine.
- The pre-wait costs 0 ms on a tree whose newest file is older than the clock. A newest file 10 ms after the clock costs about 10 ms in `build`. A file dated in the future costs no wait, and the tree rebuilds on each command.

## Known limits

- Files restored with old mtimes (`tar`, `cp -p`, `rsync -a`) change only the count.
- File systems that store mtime to 1 or 2 seconds (HFS+, FAT) can rebuild once on a command right after `build`.
